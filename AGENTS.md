# AGENTS.md

Guidance for coding agents working in this repository. Claude Code loads this file through `CLAUDE.md`; other agents read it directly.

Keep this file to what an agent cannot learn by reading the code: commands, environment facts, conventions, decisions and the reasons behind them, and boundaries. Do not add lists of routes, tables, tools, files, or env vars. They drift, and the code is the source of truth. The layout table below is the one map this file keeps: it names top-level directories and stays at that altitude.

## What this is

webhooks.cc is a production webhook inspection and testing service. Users capture incoming webhooks, inspect requests, configure mock responses, verify provider signatures, and forward requests to localhost with the CLI. A TypeScript SDK (`@webhooks-cc/sdk`) and an MCP server (`@webhooks-cc/mcp`) give programmatic and AI-agent access. Teams share endpoints under a pooled, per-seat subscription.

Production: `https://webhooks.cc` (app) and `https://go.webhooks.cc` (webhook receiver). The repository is public.

### Running in production

Production runs as containers on a single host: the web app and receiver images built from this repository (`apps/web/Dockerfile`, `apps/receiver-rs/Dockerfile`), Caddy, Redis, and a self-hosted Supabase project, all under Docker Compose. Images are built in CI and shipped to the host; the host never builds. The deploy workflow, compose files, and host configuration live in a separate private operations repository, not here.

A deploy builds the images for a given ref of this repository, loads them on the host, and recreates the web and receiver containers (and, where configured, the SMTP listener on the MX host). `NEXT_PUBLIC_*` values are build arguments, so changing one means a new build, not a restart. The CI job "Build Docker Images" checks on every PR that the images still build.

### Database changes

Migrations are plain SQL files in `supabase/migrations/`, numbered sequentially. There is no migration runner. Apply each file against dev first, then against prod before deploying the release that needs it (the production database is only reachable from its host):

```bash
PGOPTIONS="-c lock_timeout=5s" psql "$SUPABASE_DB_URL" --set=ON_ERROR_STOP=1 -f supabase/migrations/<file>.sql
psql "$SUPABASE_DB_URL" -c "NOTIFY pgrst, 'reload schema';"
```

Two rules that are easy to miss:

- After adding or changing an RPC, column, or policy, run the `NOTIFY` above. PostgREST caches the schema, and new RPCs return 404 until it reloads.
- Keep the psql invocation as shown: plain autocommit mode, because some migrations use `CREATE INDEX CONCURRENTLY` and `NOT VALID` constraints that fail inside a transaction; `ON_ERROR_STOP` so a failed statement halts the run instead of leaving a half-applied file; a short `lock_timeout` so a DDL lock wait cannot stall production traffic.

## How it fits together

Web (3000), receiver (3001, plus a private mail listener on 3002), the SMTP listener for `mailhooks.cc` on its own box (25), a self-hosted Supabase instance (Postgres, Auth, Realtime), a Cloudflare Worker that outbound deliveries go through, and optional Redis for the web app's distributed rate limiting.

Capture path: a sender POSTs to `go.webhooks.cc/w/{slug}/...`. The receiver validates the slug, strips proxy headers, and calls the `capture_webhook()` stored procedure once. That single call looks up the endpoint, checks expiry, decrements quota atomically, inserts the request, bumps counters, and picks the billing pool. The receiver answers with the configured mock response or a plain 200. Dashboards update over Supabase Realtime; the CLI streams over SSE from `/api/stream/{slug}`.

Decisions worth knowing, with the reasons:

- **The receiver talks to Postgres directly** (`DATABASE_URL`), not through the web app. One fewer hop on the hot path, and the stored procedure keeps quota and counters atomic. In production it connects to Postgres on the same Docker network rather than through Supavisor: on one host the pooler only costs CPU, and a load test sustained about twice the throughput without it.
- **DB failures are classified.** Transient errors (pool timeout, connection loss, SQLSTATE classes 08/40/53/57/58) return 503 with `Retry-After: 5` so senders retry; at-least-once delivery beats silent loss. Permanent errors fail open with 200 and are logged and counted in the receiver's once-a-minute `counts` log line (`capture_failed.<kind>`). NUL bytes in bodies and paths are sanitised (raw bytes kept in `body_raw`) instead of failing the insert.
- **RLS is deny-by-default for client roles.** Anonymous users cannot read endpoints, requests, or device codes, and may only read published blog posts. Guest dashboard reads and guest endpoint creation go through server routes using the service role. Client roles have no write access to `users`, `endpoints`, or `api_keys` (migrations 00037 and 00045; every write goes through a server route that validates, rate-limits, and audits it) and no EXECUTE on `public` functions unless a migration grants it (00037 revoked them and reset the default privileges). Team members can read shared endpoints through `can_view_team_endpoint()`, which also lets them join the endpoint's Realtime topic.
- **Live updates are Realtime Broadcast signals, not `postgres_changes`.** Triggers send `realtime.send()` signals carrying only ids on private topics (`endpoint:<id>` for request and deletion events, `user:<id>` for plan, billing and quota-state changes), and clients re-read through the authenticated routes. `postgres_changes` evaluates every change against every subscriber's RLS inside Postgres, which capped live updates far below capture throughput; a broadcast topic is authorized once per join by the `realtime.messages` policy (`can_join_realtime_topic()`). Keep `requests`, `endpoints` and `users` out of the `supabase_realtime` publication, and do not signal per capture on the user topic. The self-hosted Realtime tenant has its own rate limits (`max_events_per_second` and friends in `_realtime.tenants`) that drop messages above them.
- **Sensitive routes want a session, not an API key.** Account deletion and billing mutations reject API keys with 403.
- **Teams are billed per team.** A Polar seat subscription on the `teams` row buys the member cap and a pooled quota of seats x 100,000 requests per 30 days. `users.plan` stays free or pro and does not gate team access. `capture_webhook()` bills an endpoint shared with an active team against that team and stamps `requests.team_id`; team-billed requests keep 31-day retention regardless of the owner's plan. Each team gets its own Polar customer of type team: Polar allows one customer per email per organisation, so the owner's personal customer is never reused. Seat increases are billed at once (Polar `invoice`); seat reductions take effect at the next renewal (`next_period`), mirrored in `teams.pending_seats`, which also caps members until then. Never log a raw Polar SDK error: its message embeds the response body, which can echo customer emails; use `loggablePolarError()` from `lib/polar.ts`. The SDK is imported from a versioned entry point (`@polar-sh/sdk/2026-10`) and hands back Polar's snake_case JSON unchanged, timestamps as ISO strings. Webhook payloads follow the API version set on each webhook endpoint in the Polar dashboard, not the SDK's, so move the endpoints along when the SDK version moves.
- **Extra requests are add-on subscriptions and orders on the plan's Polar customer.** Pro and Business accounts and subscribed teams buy 25,000-request blocks three ways (migration 00065, `lib/supabase/capacity-billing.ts`): monthly blocks (a unit-priced subscription), one-time blocks (unit-priced orders, never expire) and overage (a subscription with only a metered price). A capture spends, in order, the allowance (`request_limit + block_requests`, still one conditional update), then one-time blocks, then overage up to the customer's per-period maximum (`take_extra_request()`); `requests_used` counts the allowance only, so blocks bought later are never eaten by what came after it. The add-on subscriptions' billing period is moved onto the plan's (`current_billing_period_end`), only ever earlier, so they renew and bill together and a renewal race cannot hand out a free month. Adding monthly blocks mid-period is a one-time order at the full monthly price (the user's choice, and Polar's off-session charges need its support to enable) followed by a `next_period` unit change; removing them waits for the renewal. Overage counts land on the account row and the web app's reporter (`lib/billing/overage-reporter.ts`) sends them to the Polar meter as events whose external id is the counted range, so a resend is dropped as a duplicate. The organisation allows several subscriptions per customer for this, so the Polar webhook routes add-on products before the plan handlers, which would otherwise read their events as the plan's, and add-ons are reconciled with the plan's stored state after every plan event (they end with it). Account and team deletion revoke them first, because their rows cascade away.
- **Parsed pages are sold like requests, and only with Business.** Business and Team Business buy 1,000-page blocks the same three ways (migration 00070; the `resource` of each add-on in `capacity-billing.ts`, meter event `page.overage`), spent after the plan's pages by `take_parsed_pages()`. They need the plan that allows them: a plan change away from Business, or ending Team Business, sets them to end with the period, and they cannot be started or kept while that change waits, because they would renew and charge after the plan is gone. One-time page blocks stay on the account.
- **Custom inbound domains are routed in the database, and extra ones are add-ons.** A Business account (or a Team Business team) adds its own domain (migration 00072): a TXT record `_mailhooks.<domain>` with its token and MX records that all point at `MAIL_MX_HOST` verify it, the web app's checker (`lib/supabase/inbound-domains.ts`, public resolvers from `DOMAIN_DNS_SERVERS` so a customer's nameservers never see our host) checks again every day and lapses a domain after three failed checks, counting checks the owner asks for too, and the receiver resolves each recipient at a domain it does not own through `resolve_inbound_recipient()` (local part, then the catch-all), caching the list of live domains for `INBOUND_DOMAINS_REFRESH_SECS`. Domains past `inbound_domains_allowed()` (the plan's `custom_domains` plus `extra_domains`) stay listed but are refused, the most recently verified first, so buying fewer never deletes anything. Extra domains are a capacity add-on (migration 00073, `resource: "domains"`): monthly units and the full-price mid-period add like monthly blocks, no one-time form and no overage, so paid domains that cannot renew are reported for a refund instead of kept as credits. Only a verified domain is held: when another account proves the domain with its own TXT record and the holder's is gone, the holder's row lapses at once, since whoever controls the DNS now owns the mail. A domain where any account has its email is refused, and verified domains join the capture domain in the GoTrue hook, in a trigger on `auth.users` that refuses either as a changed email (the hook only sees signups), and in every agent path that creates or names an account, because their mail is readable here.
- **Zapier and Make are REST hooks on destinations.** Both apps (`packages/zapier-app`, `packages/make-app`) connect with an API key and add a JSON destination (email only) to the chosen endpoint when a Zap or scenario turns on, and delete it when it turns off, so they get the same signed `email.received` JSON, parsed fields included, as any destination, through the same queue, filters and retries; samples come from `POST /api/requests/{id}/render` with `format: "json"`, the same payload a hook receives, attachment links included. A destination whose URL answers 410 Gone (what both platforms answer for the hook of a removed Zap or scenario, and so a destination left behind when an unsubscribe failed) is turned off rather than retried. The routes they call count their rate limits per account, not per address, because each platform sends every customer's calls from a few shared addresses. They need no routes of their own: change the destinations API, the request list or the render route, and run both packages' tests against the dev server.
- **AI only writes patterns, and only when asked.** AI setup and repair (migration 00075, `lib/ai/`) sends emails a person picked (1 to 5 of the endpoint's own, subject, sender, recipients, text and headers, never attachments) to Anthropic (`claude-opus-5-5` through `@anthropic-ai/sdk`, structured output, server-side fallbacks) only with `consent: true` on that request, from a session, never an API key. The samples go in as JSON and the system prompt calls them untrusted data; whatever the model answers is compiled with RE2 and run on every sample (`emailFieldsProblems`, `emailFieldValues`), and only fields that find a value in each are returned, once more with feedback if none did. Nothing is saved by the assist itself: proposals go through the usual layout and field editors. Each ask takes one of `plan_entitlements.ai_assists` in a rolling 30 days, per billing account (`take_ai_assist()`, the team the endpoint is billed to, else its owner), and is given back when the model or our side fails; a use row holds who, when and how it went, never what was sent. The feature is offered only with `ANTHROPIC_API_KEY`; `AI_API_BASE_URL` points tests at a fake model. Anthropic is listed on `/subprocessors`. AI never runs over live mail.
- **File drops leave from the MX host.** A destination of format `file_drop` (migration 00074, Business) writes CSV, XML or JSON files to the owner's SFTP, FTP/FTPS or S3-compatible server; the forwarding worker delivers them like Sheets rows (one claim per destination, a file per request or `claim_drop_batch()` for everything waiting once the oldest is due, the destination's delay being the batch window). Every connection, FTP data connections included, goes through `openDropSocket()` in `lib/drops/connect.ts`: in production through the SOCKS5 egress in `apps/mx-rs/src/egress.rs` (`FILE_DROP_PROXY_URL` on the web app, `MX_EGRESS_LISTEN` and `MX_EGRESS_SECRET` on the MX host, private network only), which resolves names itself and refuses private and reserved addresses (plus `MX_EGRESS_DENY`, the hosts' own public addresses), so a customer's server sees the MX host's address and never the web host's; without the proxy, drops are offered only outside production, and `MX_EGRESS_ALLOW_PRIVATE` works only in a debug build. The egress answers a CONNECT with the address it reached, and an FTP data connection goes to that address rather than the name. A drop is bounded: at most two run per process, every connection of one ends at a 4-minute deadline inside its 5-minute lease, every operation has its own timeout, and an FTP server's replies are capped, so a slow or hostile server fails its own drop and never holds the forwarding worker. The FTP client is our own so that a data connection always goes to the control host, never to the address a PASV reply names. Secrets (`drop_secret_encrypted`) are write only, read only together with the config they were saved for, and asked for again whenever the drop's server, login, pinned host key or certificate fingerprint changes, so a stolen API key cannot redirect the stored password; SFTP host keys are pinned on first use by `pin_drop_host_key()`, only while the drop still names the server that was reached. Files are written under a unique temporary name and renamed, and named after the first request, so a retry replaces its own file. The MCP server does not offer drops, so an agent never handles a server password.
- **Plan changes follow what Polar allows.** Business is a plan product like Pro ($29 monthly, $290 annual); the webhook reads the plan and interval from the product id (`planForProduct()`). Polar refuses `reset` proration for this organisation, so Pro to Business monthly applies at once with `invoice` (Polar charges the difference for the rest of the period) and the webhook grants the new plan's extra requests and pages in the same proportion (`request_limit`, and `prorated_pages` for the window in `prorated_window`); the `users_end_plan_proration` trigger restores the plan's own allowance when the period moves, the cron fallback included, so a charge for part of a period never buys a whole one. Every other change is `next_period`: Polar holds it as `pending_update`, mirrored in `users.pending_plan`, and keeping the plan sends `pending_update: null`.
- **The visual style is chosen in the browser, before paint.** Clean is the default; Account > Appearance (signed in) switches a browser to classic or back, and the inline script from `appearanceBootstrapScript()` in `apps/web/lib/ui-style.ts` applies the stored pick to `<html>` before React loads, so a page never re-skins in front of the visitor. The pick is kept in localStorage, not on the account, so it stays with the browser across sign-outs. The earlier A/B split (PostHog experiment, `NEXT_PUBLIC_UI_STYLE_SPLIT`) is retired; a style it assigned no longer counts, only a pick the visitor made.
- **Plans are rows, not names.** `plan_entitlements` (migration 00067) holds every limit and feature that differs between plans (free, pro, business) and team kinds (team, and team_business with the Team Business add-on): requests, quota period, retention, parsed pages, layouts, AI assists, domains, file drops, add-on eligibility, annual billing. SQL functions read it instead of comparing plan names, and `lib/entitlements.ts` mirrors it; an integration test compares the two, so change them together. `users.period_start`/`period_end` are the quota period everything reads; `billing_interval` and `billing_period_end` are the subscription's, so an annual plan's quota renews every month (`process_billing_period_resets()`) while its billing period runs for the year.
- **Retention is per account and per endpoint, deleted in small batches.** `cleanup_expired_requests()` (every 10 minutes, bounded batches through the existing indexes) deletes each account's personal rows past its plan's retention, team-billed rows past the team's, and an endpoint's rows past its own shorter `retention_days`; `cleanup_delivered_requests()` (every minute) does "deliver, then delete" (`delete_after_delivery`) once no delivery or parse is pending and the last one finished a few minutes ago (alerts read them). A downgrade keeps the old retention for 7 days (`retention_floor_days` until `retention_floor_until`). Reads hide rows past retention that the cleanup has not reached yet.
- **Captured email lives in object storage when it is configured.** The receiver stores each email's exact message (`m/{request_id}/raw.eml`) and decoded attachments (`m/{request_id}/a/{i}`) in S3-compatible storage (`OBJECT_STORAGE_*`, Hetzner in production, EU) before calling `capture_webhook()` with the request id it chose and the prefix; a failed upload answers transient, so the MX host says "try later" and the sender retries. Such rows keep `body` as before but no `body_raw`, and `email.raw_stored` is set. A row trigger queues the prefix of every deleted request that has one (whatever deleted it), and the web app's deleter (`lib/storage/deleter.ts`) removes the objects; the bucket's lifecycle rule (expire `m/` after 100 days) is the backstop. Downloads go through the web app (`/api/requests/{id}/raw`) or presigned links, never a public bucket.
- **Layouts parse an email before it is delivered.** An endpoint's `layouts` (migration 00069) pick, by the rule language, how an email is read: fields, line items, attachment parsing. `capture_webhook()` queues a `request_parses` job instead of the deliveries for an email on an endpoint with layouts; the web app's parse worker (`lib/parsing/worker.ts`) leases jobs, runs the layout with RE2 and `apps/parser-rs` for attachments, and `complete_request_parse()` queues the deliveries (after five failed tries it completes without a result, so mail is never held back for good). The parser is a separate binary that sandboxes itself (rlimits, seccomp, no network or files) because attachments are hostile input; the web image builds it and ships it at `/app/bin/webhooks-parser` (`PARSER_BIN` overrides). Each file's full parse is stored beside the email (`m/{id}/p/{i}.json`), so a replay or the preview reads it again and never charges twice; the preview never runs the parser. Pages are charged all or nothing by `take_parsed_pages()`: the allowance, then one-time credits, then overage. `parsed.lineItemColumns` exists because `jsonb` does not keep an object's key order. The plan's layout cap (`layouts_cap()`) only limits which layouts are matched; layouts past it are kept.
- **Free periods are lazy.** `period_end` is unset until the first capture triggers `start_free_period()`.
- **No trigram indexes on `requests`.** Search is substring `ILIKE` over path, body and headers without an index (migration 00044 dropped them): the indexes made every capture write about 8x the WAL and cost about a third of capture throughput, for a feature used rarely. Slug-scoped searches read only that endpoint's rows through `requests_endpoint_time`. Do not add a GIN index on `body` or `headers` without measuring capture throughput.
- **Capture-domain addresses never become account emails.** Mail to `mailhooks.cc` can be read through webhooks.cc itself, so it proves nothing about who holds an address. A GoTrue before-user-created hook (migration 00052, enabled in the Supabase override, see `infra/supabase/gotrue-email-auth.md`) refuses them for every signup path, and agent registration refuses them in the app (`isCaptureDomainAddress`), because admin `createUser` skips the hook.
- **Email is an ordinary request.** Email capture lands mail for `{slug}@mailhooks.cc` as a request with `kind = 'email'`, through the same `capture_webhook()` call, quota, billing period and counters as HTTP. The SMTP host (`apps/mx-rs`) runs on its own box, so a public MX record never exposes the production IP; it refuses unknown, guest, over-quota and oversize mail before accepting it and calls the receiver's private, HMAC-signed mail listener, which must only ever be reachable on the private network, never through Caddy. It asks a local rspamd (`MX_RSPAMD_URL`, on the same box) for a spam verdict; like the SPF, DKIM and DMARC results it is recorded for the user and never a reason to refuse, because test mail often looks like spam, and no third-party blocklists are queried (Spamhaus's free tier is non-commercial). It passes the raw message on byte for byte and keeps the hash of every message whose outcome the sender may not have learned (a 4xx, a lost reply, a crash mid-delivery), so the receiver can tell a sender's retry apart from a deliberate re-send. Endpoints without an owner get no email, because guest captures are readable by anyone who knows the slug. A sender's retry is matched in the database by the message hash, and only deliveries the MX host marks as retries are checked, so a message sent again on purpose is captured again. `check_email_recipient()` mirrors the billing selection in `capture_webhook()`; change them together. The capture domain never sends mail. The dashboard renders email HTML only inside a sandboxed `srcdoc` iframe (no `allow-scripts`) carrying its own CSP (`lib/email-preview.ts`); a `srcdoc` document also inherits the page's CSP, which is why every page allows `img-src https:` (not only the dashboard, since a document keeps the policy of the page it was first loaded as) (`lib/csp-img-src.ts`) so "Load images" works. Never render email HTML outside that frame.
- **Forwarding is a queue the web app drains.** An endpoint sends to up to 10 rows of `endpoint_destinations` (migration 00063), each with its own kinds, filter, format, templates, throttle, delay and secret. `capture_webhook()` queues a delivery row (table `email_deliveries`, which holds HTTP requests too since migration 00058; the old names stay because a rename would need compatibility views across a deploy) in the capture's own transaction for each destination that takes the kind, so a captured request is never lost before it is queued; the delay is the first `next_attempt_at`. Filters are evaluated by the worker, not in SQL, because they share the rule evaluator (`packages/sdk/src/rules.ts`) with the dashboard's preview; a turned-down delivery is settled as `skipped`, and `bypass_filter` marks a hand redelivery to one destination. The throttle is taken when queueing for a destination without a filter (no row at all for the rest) and by the worker once the filter passed for one with a filter, so turned-down requests never use up the slot. Destination URLs on the receiver's own host are refused when saved and when sent: a delivery would be captured and forwarded again, by up to 10 destinations each time. The endpoint's old `forward_*` columns and `notification_url` still read and write through `legacy_role` (`forward`, `notify`) destinations, so the API and older SDKs keep working; notifications are chat destinations (throttle 1 s, no retries) and the receiver no longer sends any. The worker runs in the web app, not the receiver (`lib/forwarding/worker.ts`, started from `instrumentation.ts`), because the email JSON is built by one function (`buildEmailJson()` in `packages/sdk/src/email/json.ts`) shared with the dashboard's JSON tab; a Rust copy would drift, and the code extraction relies on regex lookbehind Rust's `regex` lacks. Formats: an HTTP request goes out as received (`lib/forwarding/relay.ts`: the same method, the stored headers minus hop-by-hop ones, the exact bytes, `requests.query_raw`, plus `webhooks-cc-*` metadata headers signed with the forwarding secret; never `webhook-*`, which Standard Webhooks senders use themselves), an email as signed JSON, either kind as the owner's JSON template (`{{ placeholders }}` filled from the request, signed like the JSON format) or as a chat message when the URL is a Slack or Discord webhook (`lib/forwarding/chat.ts`, pinned by `lib/forwarding/chat-vectors.json`). Claims are leased and re-checked under `FOR UPDATE SKIP LOCKED`, so several processes can run it and a crash only delays a retry. Deliveries go through the notify-proxy Worker when `NOTIFY_PROXY_URL` is set (`X-Proxy-Mode: forward` for JSON, `relay` for requests as received), so deploy the Worker before a web release that depends on a change to it; without the proxy the web app applies the receiver's SSRF rules and pins DNS.
- **One rule language and one placeholder syntax.** Response rules (which answer a sender gets) and forwarding filters share the conditions in `packages/sdk/src/rules.ts`; mock responses and forwarded payloads share the `{{ path | filter }}` placeholders in `packages/sdk/src/placeholders.ts`. The receiver evaluates rules and fills in mock responses in Rust (`handlers/rules.rs`, `placeholders.rs`, `values.rs`), the web app with the SDK; both run `packages/sdk/conformance/rules.json` and `placeholders.json`, so change them together and regenerate the vectors. Regular expressions are RE2 on both sides (the `regex` crate, `re2js` in `lib/rules.ts`), never JavaScript's `RegExp`: they run against whatever anyone sends, and RE2 cannot backtrack. Placeholders only fill in values, with no loops or conditions (rules choose), so rendering always finishes, and an unknown first key is sent as written so old bodies never change.
- **One app serves two sites.** webhooks.cc and mailhooks.cc (the mail-first front door) are the same Next app, accounts, endpoints and billing (`lib/site.ts`). The site comes from the Host: `proxy.ts` resolves it against the two configured origins only (`NEXT_PUBLIC_APP_URL`, `NEXT_PUBLIC_MAILHOOKS_URL`, a build argument; unset means one site), passes it on in `x-whk-site`, lets mailhooks.cc answer only its own paths (the rest 308 to webhooks.cc) and keeps `app/mailhooks` off webhooks.cc; `next.config.ts` serves `app/mailhooks` at the mail host's root with host rewrites, so those pages stay static, and only the app's own layouts read the site from the request. Sessions stay per host (Supabase cookies have no domain), so everything that hands a browser back returns to the site it started on: `/auth/confirm` sends a mailhooks.cc link opened on webhooks.cc (GoTrue's site URL) to mailhooks.cc before verifying, `resolveRedirectBase` only ever answers one of the two origins, checkouts and invites return to the request's site (`returnOrigin`), and emails sent by background jobs link to `users.home_site`, the site the person last signed in on. The OAuth server, agent identities and the MCP server keep webhooks.cc as their issuer on both. Locally, run the two sites as `webhooks.localhost` and `mailhooks.localhost`: Next turns a redirect to its own `localhost` origin into a relative one, which loops between the sites.
- **Guest endpoint creation is bot-gated.** `POST /api/go/endpoint` returns 403 for crawler or missing user agents, and the landing page only auto-creates an endpoint after a human input signal. Browsers with `navigator.webdriver` get a manual create button, so Playwright and agents must click it and tests must send a browser user agent.
- **Site totals survive deletes.** `site_stats.total_webhooks` is `sum(endpoints.request_count) + deleted_webhooks`; an AFTER DELETE trigger on `endpoints` (migration 00038) moves the counts of deleted rows into `deleted_webhooks`. Do not add another accumulate step to any delete path.
- **State changes leave an audit trail; webhook traffic leaves only counts.** Routes that change account, team, billing, API key, or endpoint state call `auditUserAction()` from `lib/audit.ts`, and the Polar webhook calls `auditPolarEvent()`; both write `audit_events` (kept a year) and print one `[audit]` line, and never throw. Add the call when you add such a route. Password changes never pass through a route (the browser talks to GoTrue directly), so a trigger on `auth.users` records them instead (migration 00061), with no `[audit]` line. Individual webhooks are never logged: `capture_webhook()` upserts per-endpoint daily counts into `endpoint_daily_stats`, which outlives request retention and endpoint deletion.
- **Errors and logs go to StatOSS** (our own monitoring service), when `STATOSS_DSN` is set; the web app, the receiver and the MX host are one StatOSS app each. Report what is our fault and needs someone: the web app through `reportError()` in `lib/observability.ts`, the Rust services with `tracing::error!`. A customer's URL failing, a 4xx or a rate limit is not an error. One failure tends to repeat for every request, so each call site sends at most one event a minute and the rest go as log lines (`console.error`, `warn` and `info` on the web server; `info!` and up in Rust), themselves capped per minute. The clients send from a thread or queue of their own and drop when StatOSS is slow or down; a capture never waits on them. Never put request or email contents in an error or a log line; the web app also replaces email addresses with `[email]` in what it sends, and keeps the `[audit]` lines (which `audit_events` holds) out of StatOSS. Browser errors go to a fourth app (`lib/observability-browser.ts`, DSN inlined at build time): a browser DSN is public, so that app's key only accepts webhooks.cc origins at a low rate and the app may use only part of the team's monthly errors, which keeps a flood from starving the server apps. Its source maps are uploaded during the Docker build and deleted, never served. To investigate, read StatOSS yourself rather than asking for screenshots: the REST API at `https://statoss.com/api/v1` (`/issues?app=<slug>&status=all`, `/issues/<id>` with its latest event, `/logs`) or `npx statoss logs search|tail --app <slug>`, with a read key as a bearer token or `STATOSS_API_KEY`. The apps are `webhooks-cc-web`, `webhooks-cc-receiver`, `webhooks-cc-mail` and `webhooks-cc-browser`; an event from `onRequestError` carries the route pattern and method in its tags, and the digest when Next gave one.
- **Outbound deliveries hide the origin IP** by going through the Cloudflare Worker when `NOTIFY_PROXY_URL` is set; otherwise the web app delivers directly with SSRF-safe DNS pinning.
- **Email/password auth is GoTrue configuration, not app code.** SMTP, minimum password length 8, and the template URLs live in the Supabase instance's `docker-compose.override.yml`; see `infra/supabase/gotrue-email-auth.md`. Email links carry a `token_hash` to `/auth/confirm`, which verifies server-side. If GoTrue could not fetch the templates at startup it keeps serving its defaults until the auth container restarts.
- **Agent registration follows auth.md v0.6.** An agent registers, gets a signed identity assertion, and exchanges it for short-lived access tokens that are ordinary `whcc_` rows in `api_keys`, so the bearer path and every route accept them unchanged; each exchange reads the registration again, so revoking it ends everything at once. Pre-claim tokens have no user: every consumer of an API key must tolerate a null user, and the routes that need one refuse them, which confines them to the sandbox. Sandbox endpoints belong to the registration, never to a user, so guest reads and the guest claim must keep skipping them; they have their own pool, budget and billing key in `capture_webhook()`. A claim (the human signs in and types the agent's code; the email the agent named decides who may) adopts them into the human's account in one transaction, deletes the pre-claim tokens, and lets the agent collect account tokens once with its claim token; claimed agent tokens are capped as connected agents, not counted as API keys, and never reach session-only routes. The proof of work on anonymous registration only raises the cost of scripted abuse; the rate limits, the live cap and the pool are the real bounds. `AGENT_IDJAG_PROVIDERS` stays empty in production until a real ID-JAG issuer exists. An ID-JAG identity `(iss, sub)` never binds silently to an existing account: without a delegation on file, an account with its verified email gets `interaction_required` and the same claim ceremony (`link_agent_idjag_identity()`, migration 00057), only an account created for the email in that request links at once, `auth_time` must be recent on every presentation, and a provider's Security Event Token at `/api/agent/event/notify` revokes the delegation with its tokens. The protocol itself is documented in `/auth.md` (`lib/agent/metadata.ts`).
- **Agents keep their registrations in one shared file.** The MCP server, the TypeScript, Python and Go SDKs and the CLI read and write `~/.config/whk/agent.json` (XDG, macOS and Windows rules, `WHK_AGENT_FILE` override; the CLI's `token.json` lives beside it), so a connection a human approved once survives restarts and works from every tool. The format and the rules (live slots, the cached access token, atomic 0600 writes, what `invalid_grant` removes) are in `packages/sdk/conformance/agent-credentials.md`, and every implementation runs `agent-credentials.json`; change them together. The claim token is never written, as `/auth.md` asks, so only the process that registered a sandbox can move its endpoints into an account; a later one connects the human through a service_auth registration. An explicit API key always wins over the file.
- **The remote MCP server is the stdio server's tools behind OAuth.** `/mcp` (`app/mcp/route.ts`, `lib/mcp/hosted.ts`) runs `registerTools()` from `@webhooks-cc/mcp/tools` on the v2 MCP SDK (`@modelcontextprotocol/server`), statelessly, for the 2026-07-28 revision and the 2025 fallback; the stdio server stays on the v1 SDK, so add tools in `packages/mcp/src/tools.ts` once for both. Tools act through the SDK over loopback (`MCP_INTERNAL_API_URL`, default `http://127.0.0.1:$PORT`) with the caller's own token and address, so the API routes authenticate, rate-limit and audit as for any client; tools that post to a URL the caller names (`send_to`, `replay_request`, `targetUrl`) are left out because they would run from the box's network, the sends that remain (`send_webhook` to a capture URL) leave through the notify proxy so a capture never shows the box's IP, and waits are capped (50 s, polls 1 s apart at least, 8 tool calls running at once per account, counted around the handler because a 2025-era client's answer streams back before the tool finishes; no JSON-RPC batches). The OAuth server (`lib/oauth/`, migration 00066) is authorization code with PKCE for public clients only: Client ID Metadata Documents (fetched through the notify proxy like forwarding, so the box's IP stays hidden; the proxy returns 1 KB, the limit for a document) and dynamic client registration. A grant is an agent registration of kind `oauth`, claimed at once, so it shares Connected agents, the cap and disconnecting with claimed agents; its access tokens are `whcc_` rows and its refresh token rotates (a rotated token presented again within a minute gets a new pair and supersedes the one it lost; later, or a superseded token at any time, revokes the grant). Client ids and redirect URIs on our own hosts are refused (anyone can serve a document from a capture URL). The consent page posts with the session's bearer token, never a cookie, navigates to the redirect itself (`form-action 'self'` would block a redirect after a form post), and only after the human clicks: a refused request is shown, never redirected, since a dynamically registered redirect URI proves nothing. Scopes are advisory, as for every agent token.
- **Share links are frozen copies.** `/s/{token}` shows a snapshot taken when the link was made (`request_shares`, migration 00062), with credential headers always removed and signature and token headers removed by default, so a link keeps working after retention deletes the request and never shows more than it did. Shares cascade from their endpoint and account but deliberately have no foreign key to `requests`: it would add a cascade trigger to every delete on that table. Only the endpoint's owner can share, because a team member's links would outlive their membership out of the owner's sight; the account's Share links page lists every live link, since a link outlives the request whose dialog made it. Creating and revoking take a session, never an API key, because a link publishes data to anyone who holds it. Analytics and error reports never see a token: PostHog's `before_send` and the StatOSS redaction both rewrite `/s/{token}`, and elements showing a token carry `ph-no-capture` so session recordings skip them. The page is `noindex` and its unfurl metadata never includes the request.
- **The agent skill tells agents when to use the MCP tools.** `plugins/webhooks-cc/skills/webhook-testing/SKILL.md` is the one copy: Claude Code installs it with the MCP server as a plugin, and other agents through `npx skills add kroqdotdev/webhooks-cc`, which finds it through the marketplace file. An MCP test fails when the skill names a tool the server no longer has, so rename tools in both places. The MCP release workflow also publishes `packages/mcp/server.json` to the official MCP Registry under `io.github.kroqdotdev/` (GitHub OIDC, no secret); a test keeps its version equal to the package's.
- **Adding a webhook provider** touches the SDK catalog, the web editorial data in `apps/web/lib/webhook-provider-pages.ts`, the pinned counts in the MCP tests, the SDK conformance vectors, the Python SDK's `templates.py` and `verify.py` (its tests compare the provider lists with `templates.ts`), the Go SDK's `internal/templates` and `verify` packages (the same check), and a migration that extends the `check_signing_config` CHECK constraint on `endpoints`. The constraint is the one people forget; the signature-verification integration test is what catches it.
- **The TypeScript SDK is the reference for every SDK.** `packages/sdk/src/__tests__/conformance.test.ts` writes JSON vectors (signing, verification, forwarding signatures, matchers, durations) to `packages/sdk/conformance/`, and SDKs in other languages run them in their own CI, so their behaviour cannot drift; the Python and Go SDKs (`packages/sdk-python`, `packages/sdk-go`) read them straight from that directory. Go takes `time.Duration` rather than duration strings, so it skips `durations.json`. The test fails when a file is stale: after a deliberate change to signing or verification, regenerate with `pnpm --filter @webhooks-cc/sdk exec vitest run conformance -u` and port the change. Email codes and links are computed only in TypeScript and served by the request routes on `extracts=true` (opt-in, because up to 20 links can break the MCP server's output budget), so ports never reimplement the extraction; the same goes for the reply text and an endpoint's named email fields (`emailFields`), whose owner-written patterns run only on the server with RE2 (`lib/email-fields.ts`; the dashboard asks the server rather than ship RE2 to browsers). The inbound provider shapes (Postmark, SendGrid, Mailgun, CloudMailin) are built by the SDK (`packages/sdk/src/email/inbound.ts`) and served to the CLI's tunnel and the other SDKs by `POST /api/requests/{id}/render`.

## Environment

Env vars are validated with zod in `apps/web/lib/env.ts` and loaded in `apps/receiver-rs/src/config.rs` and `apps/mx-rs/src/config.rs`; read those for the current list and defaults. `.env.example` documents the required set. Secrets live only in `.env.local`, which is gitignored. Three that trip people up:

- `DATABASE_URL` (receiver) is the session pooler in development and a direct same-host connection in production. Keep `PG_POOL_MAX` small (about 20) whenever it bypasses a pooler: every capture updates the same user and endpoint rows, and hundreds of direct connections only queue on those row locks. For the same reason the receiver caps concurrent captures per billing account (`CAPTURE_MAX_INFLIGHT_PER_ACCOUNT`, default 4, keyed by the `billing_key` that `capture_webhook()` returns): without it one flooded account fills the pool and every other account waits. `SUPABASE_DB_URL` is the direct connection used for migrations.
- `SIGNING_SECRET_KEY` (AES-256-GCM, base64, 32 bytes) is needed by both the receiver and the web app once signature verification is configured. Generate with `openssl rand -base64 32`.
- Polar, SMTP, StatOSS, and Redis are optional in development.

## Conventions

- **Branch and PR for every change.** `main` requires linear history, signed commits, and a PR; only squash or rebase merges are allowed. Commits are GPG-signed locally.
- **Reviews.** CodeRabbit and CodeQL comment on every PR (Codex too, when its subscription is active; it is off for now); address their findings before merging. CodeRabbit reviews only when asked (`@coderabbitai review`), about once an hour. CI runs lint, typecheck, the web build, the SDK, MCP, and web unit suites, and the Rust build, test, and clippy jobs. Web integration tests and Playwright do not run in CI, so run them locally when you touch the web app.
- **Version and changelog on every web PR.** Bump `APP_VERSION` in `apps/web/lib/changelog.ts` and `version` in `apps/web/package.json` (patch for fixes and small features, minor for significant features, major reserved for 1.0) and add a `track: "web"` entry at the top of the web section. CLI, SDK, and MCP releases bump `CLI_VERSION`, `SDK_VERSION`, or `MCP_VERSION` and add an entry on their own track when the tag is cut (`v*`, `sdk-v*`, `mcp-v*`). A unit test keeps the SDK and MCP constants in sync with the package versions. The Python SDK's version lives in `packages/sdk-python/pyproject.toml` and `src/webhooks_cc/__init__.py`; a `sdk-python-v*` tag publishes it to PyPI through trusted publishing (no token), and the workflow refuses a tag that does not match the version. The Go SDK's version is `Version` in `packages/sdk-go/doc.go`; Go modules are published by their tags, so a release is the tag `packages/sdk-go/v<version>` (the module sits in a subdirectory), pushed after the web release whose `/go` route serves the `go-import` tag; the release workflow checks the tag against `Version` and has the module proxy fetch it.
- **Tests live next to the code they cover.** Unit tests as `*.test.ts` beside the source, web integration suites in `apps/web/tests/integration/`, Rust tests in each crate. Scratch verification scripts stay out of the repo.
- **Design system.** The UI ships in two styles: clean, the default (paper and ink: a cool paper canvas, white surfaces with hairlines instead of shadows, one pine green for buttons, links and selection, IBM Plex Sans with IBM Plex Mono), and classic (neobrutalist, Space Grotesk), which a signed-in user can pick under Account > Appearance along with light or dark mode. Both share one component tree; every page gets its header from `components/nav/site-header.tsx`, anchored at the top, with page context passed as children; `data-style` on `<html>` swaps the tokens, independently of light and dark mode. Write classes with the style-aware vocabulary documented at the top of `apps/web/app/globals.css` (`border-strong`, `border-line`, `shadow-raised`, `caps`, the `ui-*` classes) instead of raw `border-2 border-foreground` or `uppercase tracking-wide`; `lib/ui-style-contract.test.ts` fails on the classic-only utilities. Check new UI in both styles, and reuse the shadcn/ui primitives in `components/ui` rather than introducing new styling patterns.
- **Formatting.** Prettier and ESLint are enforced in CI; run `pnpm format` before committing. `apps/web/public/email-templates/` is excluded because Prettier breaks Go template actions.
- **No em dashes** anywhere: code, comments, docs, commit messages.

## Boundaries

- Production is real and serves paying users. Do not deploy, restart production services, apply migrations to production, publish packages, or change Polar or Supabase instance configuration unless the task explicitly asks for it. Production runs on a separate host and deploys through the private operations repository; do not build or deploy from a development machine.
- Ask before anything that costs money or sends real email: Polar checkouts, invites to real addresses, notification tests against third-party URLs.
- Never source `.env.local` wholesale in shell scripts or paste secrets into logs, PR bodies, or commit messages. Extract single variables when needed.
- The repository is public, and git history cannot practically be scrubbed: customer names, email addresses, endpoint slugs, team ids and billing details never go into code, tests, comments, commit messages, or PR and issue text. Describe a customer report generically ("a customer reported") and use neutral examples (Acme, made-up slugs).
- New `public` functions are service-role only. Grant client EXECUTE in a migration only when the function is meant to be called from the browser.
- Never add `revoke` or `grant` statements to `handle_new_user()`; it runs as `supabase_auth_admin` from an auth trigger.

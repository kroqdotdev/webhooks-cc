All available commands for the `whk` CLI.

Run `whk` with no arguments to print the list of commands. Every command prints plain text, or JSON with `--json`, and reports failures with the [exit statuses](/docs/cli#scripts-ci-and-ai-agents) listed in `whk --help`.

## Global flags

These work with every subcommand.

| Flag            | Description                                                         |
| --------------- | ------------------------------------------------------------------- |
| `--json`        | Print the API's answers as JSON (NDJSON for streams) and failures as `{"error": {...}}` on stderr |
| `--api-url`     | Use another API base URL (also: `WHK_API_URL`)                      |
| `--webhook-url` | Use another webhook receiver URL (also: `WHK_WEBHOOK_URL`)          |
| `--no-color`    | Disable colored output                                              |

The first time you stop a tunnel or a share with Ctrl+C, `whk` prints a link to its GitHub repository, once per machine. It never prints with `--json`, in CI, or when the output is piped; set `WHK_NO_STAR_HINT=1` to turn it off everywhere.

## auth login

Log in to webhooks.cc. Opens a page in your browser that shows the login's code; approve it there if it matches the code in your terminal. Credentials are stored at `~/.config/whk/token.json`.

```bash
whk auth login
whk auth login --remote      # on a server over SSH: print the link, open it in your own browser
whk auth login --no-browser  # print the link without opening a browser
```

`--remote` is the default over SSH and on Linux without a display (not in WSL, where the Windows browser opens). The page warns whoever approves when a login came from a different network than their browser, or one it could not compare, and `--remote` never hides that: any terminal can claim it. Anyone who did not start the login can choose **This wasn't me** on the page, which ends it at once: `whk` stops with `login_denied` (exit status 3). With `--json`, the first line is `{"status":"pending","user_code":...,"verification_url_complete":...}` and the last `{"status":"success","email":...}`.

## auth logout

Remove stored credentials from your machine.

```bash
whk auth logout
```

## auth status

Show current authentication status and email. When you are not logged in but an agent's account connection is saved (see [sandbox connect](#sandbox)), it says the CLI acts through that connection; with `--json` the answer carries `"via": "agent"` instead of `"via": "login"`.

```bash
whk auth status
```

### Which account whk acts as

In order: an API key in `WHK_API_KEY`, but only together with `WHK_AUTH=key`; your login (`token.json`); then a saved agent connection. `WHK_AUTH=agent` uses the agent connection and ignores the login. A `WHK_API_KEY` alone, the variable the SDKs read, never changes which account `whk` acts as, so a key in your shell for another account or a CI job leaves your own commands alone. The SDKs' `share()` and the MCP server's `share_port` set both variables when they run `whk` with a key.

```bash
WHK_AUTH=key WHK_API_KEY=whcc_... whk shares ls
```

## create

Create a new endpoint. An optional name can be provided; the slug is auto-generated. It prints the endpoint's webhook URL and its email address (`{slug}@mailhooks.cc`, see [Email Capture](/docs/email-capture)).

```bash
whk create [name]
```

| Flag                 | Description                                                                                          |
| -------------------- | ---------------------------------------------------------------------------------------------------- |
| `--ephemeral, -e`    | Create the endpoint as ephemeral (it expires)                                                         |
| `--expires-in`       | Expiry duration (e.g., `12h`, `7d`)                                                                   |
| `--mock-status`      | Mock response status code (100-599)                                                                   |
| `--mock-body`        | Mock response body; [placeholders](/docs/mock-responses) such as `{{ json.id }}` are filled in per request |
| `--mock-header`      | Mock response header (repeatable, format: `Key:Value`)                                                |
| `--signing-provider` | Provider for automatic signature verification (e.g., `stripe`, `github`)                              |
| `--signing-secret`   | Signing secret (encrypted server-side, never stored locally; also: `WHK_SIGNING_SECRET`)              |

```bash
whk create my-stripe --signing-provider stripe --signing-secret whsec_...
```

## list

List your endpoints and those shared with you through teams, with slug, name, team, and URL. Your [favourites](#favorite) come first, marked with a star; the rest follow in slug order. With `--json` the answer is the API's `{ "owned": [...], "shared": [...] }`, each endpoint carrying `favorite`.

```bash
whk list
whk list --team Payments
```

| Flag     | Description                                                                                             |
| -------- | ------------------------------------------------------------------------------------------------------- |
| `--team` | Only endpoints tied to this team (id or name): shared with you from it, or yours that are shared with it |

## get

Show an endpoint's details: webhook URL, email address, name, mock response, and whether it is one of your favourites.

```bash
whk get <slug>
```

## update-endpoint

Change an endpoint's name, mock response or agent repository.

```bash
whk update-endpoint <slug> --mock-status 202 --mock-body '{"ok":true}'
whk update-endpoint <slug> --agent-repo acme/api
```

| Flag                 | Description                                                                                                                   |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `--name`             | New display name                                                                                                              |
| `--mock-status`      | Mock response status code                                                                                                     |
| `--mock-body`        | Mock response body (placeholders are filled in)                                                                               |
| `--mock-header`      | Mock response header (repeatable, format: `Key:Value`)                                                                        |
| `--clear-mock`       | Remove the mock response                                                                                                      |
| `--agent-repo`       | The GitHub repository (`owner/name`) a coding agent fixes failed deliveries in ([fix prompts](/docs/forwarding#fix-prompts)) |
| `--clear-agent-repo` | Remove the agent repository (as `--agent-repo ""` does)                                                                       |

## favorite

Mark an endpoint as a favourite, or remove it again with `unfavorite`. Favourites come first in `whk list` and in the dashboard's endpoint switcher. A favourite is yours alone: you can favourite an endpoint shared with you through a team without changing it for anyone else. Both commands are idempotent, and `favourite` and `unfavourite` work as aliases. They need an account, not an agent sandbox.

```bash
whk favorite <slug>
whk unfavorite <slug>
```

With `--json` they print `{ "slug": "<slug>", "favorite": true }` (or `false`).

## delete

Delete an endpoint. In a terminal it asks first; without one (a script, CI, an agent) it stops with `confirmation_required` (exit 9) unless `--yes` is set.

```bash
whk delete <slug>
whk delete <slug> --yes
```

| Flag        | Description                                   |
| ----------- | --------------------------------------------- |
| `--yes, -y` | Delete without asking (`--force` still works) |

## tunnel

Forward webhooks to a local port, optionally with a path (`whk tunnel 8080/api/webhooks`). The target can also name the host on this machine: `localhost:8080`, `127.0.0.1:8080/api` or `http://localhost:8080/api` (plain HTTP only). Creates a new endpoint unless `--endpoint` is set. Captured emails are posted too, as webhooks.cc's email JSON or in a mail provider's shape ([emails](/docs/cli/tunnel#emails)).

```bash
whk tunnel <port>
```

| Flag                    | Description                                                                                                                         |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `--endpoint`            | Use an existing endpoint instead of creating one                                                                                    |
| `--ephemeral, -e`       | Delete the endpoint when the tunnel exits                                                                                           |
| `--header, -H`          | Add a custom header to forwarded requests and emails (repeatable, format: `Key:Value`)                                              |
| `--email-format`        | Shape to post emails in: `json` (default, webhooks.cc's email JSON), `postmark`, `sendgrid`, `mailgun` or `cloudmailin`             |
| `--email-path`          | Path to post emails to, appended to the target like a webhook's path (default: the target itself)                                   |
| `--mailgun-signing-key` | Your Mailgun HTTP webhook signing key, to sign the form with `--email-format mailgun` (also: `WHK_MAILGUN_SIGNING_KEY`)             |
| `--no-email`            | Skip captured emails instead of posting them                                                                                        |
| `--live`                | Relay each webhook to the local server while the sender waits, so it gets your app's answer ([live tunnels](/docs/live-tunnel))       |

When signature verification is configured on the endpoint, tunnel injects verification headers into forwarded requests:

- `X-Signature-Verified: true` or `false`
- `X-Signature-Provider: stripe` (the provider name)
- `X-Signature-Error: ...` (when verification fails)

Your local server can use these headers to skip its own verification during development.

> **Warning:** These headers are injected by the local tunnel client and are **not authenticated**. Never trust them in production: any HTTP client can send arbitrary `X-Signature-*` headers. Always perform your own signature verification in production environments.

## share

Share a local port at a public link, `https://<name>.sharehooks.cc`, until you press Ctrl-C (or the process gets `SIGTERM`). The target is a port on this machine: `3000`, `localhost:3000`, `127.0.0.1:3000` or `http://localhost:3000`; paths and local HTTPS servers are refused. See [Share localhost](/docs/share); the [framework guides](/share#frameworks) list each dev server's default port and the settings that matter behind a public link.

```bash
whk share <port>
```

| Flag         | Description                                                                                  |
| ------------ | -------------------------------------------------------------------------------------------- |
| `--name`     | Share under a name you reserved, or reserve it now if nobody holds it (it counts against your plan's names); a random name otherwise |
| `--password` | Ask visitors for a password (prompted, or from `WHK_SHARE_PASSWORD`; Pro, Business and teams) |
| `--no-qr`    | Do not draw the link as a QR code                                                            |
| `--json`     | One JSON event per line (`live`, `request`, `reconnected`, `retrying`, `notice`, `stopped`, `error`); `stopped` exits 0, `error` (refused before it opened) exits 1 |

## shares

List and stop your shares, and a teammate's under a team name, and see what visitors asked for.

```bash
whk shares ls              # live shares and this month's data
whk shares ls --ended      # earlier shares
whk shares log <id|name>   # the last requests visitors made to a live share, newest first
whk shares stop <id|name>
```

`whk shares log` (also `whk shares requests`) lists each request's time, method, path, status, duration and data, with the visitor's number, device and country, never their address. `--json` prints the API's answer as it is.

`whk shares stop` also stops a share whose CLI is reconnecting after a dropped connection (within 5 minutes), so it does not come back.

## names

Names to share under (Pro, Business and teams). A name reserved inside a team belongs to the team.

```bash
whk names ls
whk names reserve <name>
whk names release <name>
whk names password <name>           # prompted, or WHK_SHARE_PASSWORD
whk names password <name> --clear
```

## listen

Stream incoming requests and emails for an endpoint without forwarding them: one line each, or one JSON object per line (NDJSON) with `--json`.

```bash
whk listen <slug>
```

Each line has the time, the method, the path (for an email, the address and the subject), the signature check when verification is configured, the size and the request id for `whk requests get`:

```
14:32:01 POST /webhook ✓ stripe  423 B  6f1c...
14:32:05 POST /webhook ✗ stripe  423 B  9a2e...
```

## wait

Wait for the next request or email at an endpoint, print it, and exit. Started before the sender, pass `--since now` so only a new request counts. Without it, requests from the last 5 minutes count too, which suits starting it after the sender ran, but can return an earlier delivery. When nothing matching arrives in time it exits with `timeout` (exit 8).

```bash
whk wait <slug> --since now --json
whk wait <slug> --kind email --since now --timeout 2m --json
whk wait <slug> --method POST --path /stripe --count 3 --json
```

| Flag | Description |
| --- | --- |
| `--timeout` | How long to wait, with a unit: `30s`, `5m`, `1h` (default `30s`) |
| `--count` | How many matching requests to wait for (1 to 100); more than one prints a JSON array |
| `--since` | `now` (only what arrives after the command starts, by the server's clock), a duration back such as `2m`, or a timestamp in milliseconds |
| `--method` | Only this HTTP method |
| `--kind` | `http` or `email` |
| `--path` | Only requests whose path (for an email, the recipient address) contains this text |

## requests

List, read, search, count, clear, and export captured requests. Run `whk requests <command> --help` for each command's flags.

```bash
whk requests list <slug>          # newest first, --limit (default 25), --since, --cursor
whk requests get <request-id>
whk requests search -q invoice --slug <slug> --from 1h   # across retained requests: --method, --kind, --to, --limit, --order, --cursor
whk requests count --slug <slug> --method POST           # same filters as search, and --cursor
whk requests clear <slug>         # --before <time or duration>, --yes to skip the prompt
whk requests export <slug> --format har -o requests.har  # or --format curl; --limit (default 100), --since
```

Captured [emails](/docs/email-capture) are listed with an `EMAIL` method, the address they arrived at, and their subject:

```
2026-10-08 16:47:20 EMAIL acme+run-7@mailhooks.cc Confirm your email 1.2 KB
```

`whk requests search` finds `-q` as a case-insensitive substring of the path, the headers or the body, and in an email's subject, text and addresses. `--from` and `--to` take a duration back from now (`90s`, `15m`, `1h`, `7d`) or a timestamp in milliseconds, so `--from 1h` searches the last hour (a duration is turned into a time once, when the command starts, so every page covers the same window); `--kind http` or `--kind email` keeps one kind, and `--limit` above 200 takes several pages. `--order` is `desc` (newest first, the default) or `asc`.

A search reads the newest requests first and keeps reading until it has `--limit` matches, reached the end, or 25 seconds have passed. When it stops before the end it says so on stderr, with the command that continues it:

```
Searched back to 2026-10-08 16:47:20; older requests were not searched. Continue with: whk requests search --api-url=https://webhooks.cc --slug=abc123 -q=invoice --from=1759934840000 --cursor=<cursor>
```

`--cursor` continues a search with the same filters and order (it cannot be combined with `--offset`); the printed command carries `--from` and `--to` as the times the first run used, and `--api-url` naming the server the first run used, so the cursor goes back to the server that issued it. `--json` prints the matches as one JSON array, as before; when the search stopped early, stderr carries one JSON line instead: `{"search":{"complete":false,"searchedUntil":...,"cursor":"...","continue":"whk requests search ..."}}`.

`whk requests count` is exact without `-q` and `--method`. With either it counts for up to 25 seconds and prints `Count: 42` when it counted everything, or `Count: at least 42 (searched back to <time>)` with the command that counts the rest, whose result you add to this one. `--json` prints `{ "count", "exact", "searchedUntil", "cursor", "from", "to" }`: `from` and `to` are the window this run counted, in milliseconds (`null` without one), so pass them with `--cursor` to count the same window on rather than a duration, which would start from the later time. When the count is not exact, stderr carries one JSON line with the command that does that: `{"count":{"exact":false,"searchedUntil":...,"cursor":"...","continue":"whk requests count ..."}}`.

`whk requests get` on a request a [live tunnel](/docs/live-tunnel) relayed adds the **Live Response**: the status the sender got and why, the first few headers and the start of the body (`--json` has the whole record as `liveResponse`).

`whk requests get` on an email shows the sender, recipient, subject, tag, attachments, and text part instead of the raw message. Add `--json` for the headers and the raw message; the HTML and the sender checks are in the dashboard.

On an endpoint with [layouts](/docs/layouts), it also shows what they found under **Parsed**: the layout, each field as `name: value`, the line items as a table in their columns' order (the first 50), and one line per parsed attachment. `--json` returns the request's `parsed` as stored: a very large result is cut to fit the email's JSON (attachment rows and text first, then line items from the end), and `parsed.truncated` says so.

## replay

Replay a captured request to a target URL. Emails cannot be replayed as HTTP requests; to send them to your server, use [forwarding](/docs/forwarding).

```bash
whk replay <request-id>
```

| Flag   | Description                                              |
| ------ | -------------------------------------------------------- |
| `--to` | Target URL for replay (default: `http://localhost:8080`) |

## send

Send a test webhook to one of your endpoints. The body can be a string or `@file`.

```bash
whk send <slug> -d '{"event":"test"}' -H "Content-Type: application/json"
```

| Flag           | Description                                         |
| -------------- | --------------------------------------------------- |
| `--method`     | HTTP method (default: `POST`)                       |
| `--header, -H` | Request header (repeatable, format: `Key:Value`)    |
| `--data, -d`   | Request body, a string or `@file` (up to 10 MB)     |

## send-to

Send a webhook from your machine to any URL, with the same flags as `send`.

```bash
whk send-to http://localhost:3000/webhooks -d @payload.json
```

## teams

Manage teams: creating, sharing, members, invites, and price quotes. Wherever a command takes `<team>`, pass a team id or a team name (case-insensitive). A name that matches several teams is rejected; pass the id instead.

```bash
whk teams list                              # your teams: role, seats, members, pooled usage, status
whk teams members <team>                    # members and pending invites
whk teams create "Payments"                 # a team you own; it needs a subscription before sharing
whk teams rename <team> "Payments EU"
whk teams delete <team>                     # asks, waits for the approval
whk teams share <slug> --team <team>        # share an endpoint you own (needs an active team)
whk teams unshare <slug> --team <team>
whk teams invite <team> <email>             # asks, waits; then sends the invite email
whk teams withdraw <team> <invite> --yes    # an invite id or the invited email
whk teams remove <team> <member> --yes      # a user id or email; frees their seat
whk teams leave <team> --yes
whk teams invites                           # invites waiting for you
whk teams accept <invite-id>
whk teams decline <invite-id>
whk teams quote <team> --seats 5            # what a seat change would cost
whk teams quote <team> --plan team_business --interval year
```

Sharing moves the endpoint's requests onto the team's pooled quota. Only the endpoint owner can share or unshare, and only the team owner can rename, invite, withdraw an invite, remove a member, or ask for a quote. Removing a member, or leaving, unshares the endpoints that member shared with the team; an owner deletes the team instead of leaving it. `remove`, `leave` and `withdraw` ask first, and need `--yes` without a terminal.

Deleting a team ends its subscription at once and takes its shared endpoints from every member, and an invite emails the address you name, so both need the team's owner to approve them, as a new API key does; once an invite is approved, whk prints it, and accepting it claims one of the team's seats. `delete` and `invite` take the same `--remote`, `--no-browser`, `--no-wait` and `--timeout` as `keys create`. `quote` only prices a change (`--interval` is `month` unless you say `year`); seat and plan changes are made in the browser. Every subcommand supports `--json`.

## billing

What the account pays for, read only: the plan and its subscription (monthly or annual, its status, when it renews, a change waiting for the renewal, whether it ends), the add-ons (extra requests, parsed pages, domains), and every team you belong to with its seats, status and add-ons. With `--json` you get the whole `/api/billing` answer. Changing a plan, seats or add-ons is done in the browser, under Account > Plan.

```bash
whk billing
```

## keys

The account's API keys. Listing and revoking act at once. A new key needs the account's owner to approve it, even when you are that owner: `whk keys create` prints a link and a code, the page shows the same code to compare, and once it is approved whk prints the key, the only time it is ever shown.

```bash
whk keys list                                   # name, prefix, created, expires, last used
whk keys create "GitHub Actions"                # asks, waits for the approval, prints the key once
whk keys create "Staging" --expires-in-days 30  # 1 to 365 days (default 90)
whk keys create "CI" --no-wait                  # print the approval and exit
whk approvals wait <approval-id>                # collect it later (any approval)
whk keys revoke <id> --yes
```

On another machine (a server over SSH), `--remote` prints the link without opening a browser, as `whk auth login` does; it is detected over SSH by itself. With `--json`, `keys create` prints `{"status":"pending","approval":{...}}` first and `{"status":"completed","approval":{...},"result":{"key":...}}` last. A refused approval exits with `approval_denied` (status 9), one nobody answered in time with `approval_expired` (status 8).

## account

The account's display name. A rename needs the account's owner to approve it, as a new key does.

```bash
whk account rename "Acme Ops"   # asks, waits for the approval
whk account rename --clear
```

## agents

The agents connected to the account: claimed agents and apps connected with OAuth, such as a hosted MCP client. Disconnecting one stops its tokens at once; the endpoints it brought stay.

```bash
whk agents list
whk agents disconnect <id> --yes
```

## share-links

Public links to a read-only copy of a request, at `https://webhooks.cc/s/<token>` (see [Share a request](/docs/dashboard-features#share-a-request)). Listing and revoking act at once. A new link publishes the request to anyone who has it, so it needs the account's owner to approve it; once approved, whk prints the link.

```bash
whk share-links list                       # every live link, with the request it copies
whk share-links list --request <id>        # one request's links
whk share-links create <request-id>        # asks, waits, prints the link (7 days)
whk share-links create <request-id> --days 30 --show-signatures
whk share-links revoke <id> --yes
```

Credential headers are always left out of the copy; signature and token headers are too, unless `--show-signatures`. `create` takes the same `--remote`, `--no-browser`, `--no-wait` and `--timeout` as `keys create`.

## domains

[Custom inbound domains](/docs/email-capture#your-own-domain) (Business, or a Team Business team with `--team <id>`, its owner only). Removing one gives it up (getting it back means verifying it again), so it needs the account's owner to approve it.

```bash
whk domains list                               # status, DNS records, routes
whk domains add inbound.acme.com               # prints the TXT and MX records to publish
whk domains verify <id>                        # looks the records up now
whk domains route <id> --route orders=orders-hook --route invoices=invoice-hook
whk domains route <id> --catch-all other-hook  # or --catch-all none to refuse other addresses
whk domains remove <id>                        # asks, waits for the approval
```

`route` takes endpoints by slug or id, and keeps what you leave out: `--catch-all` alone keeps the routes, and `--route` replaces every route but keeps the catch-all.


## google

Google accounts for [Google Sheets destinations](/docs/forwarding#google-sheets). Listing, tabs, new spreadsheets and disconnecting act at once. Connecting an account and choosing an existing spreadsheet need the account's owner: whk prints a link, and the page takes them to Google's consent page or opens the Drive picker.

```bash
whk google list                                    # connected accounts
whk google connect                                 # asks, waits, prints the new connection's id
whk google pick <connection>                       # the owner chooses a spreadsheet; prints its id and tabs
whk google create-sheet <connection> --title "Orders" --header Received --header Subject
whk google tabs <connection> <spreadsheet>
whk google disconnect <connection> --yes
```

## ai

[AI setup](/docs/layouts#set-it-up-with-ai): AI proposes email fields or a layout from 1 to 5 of an endpoint's emails. Sending them to Anthropic needs the account's owner, who sees each email by subject and sender on the approval page. whk prints the proposals once it ran; nothing is saved until you apply them.

```bash
whk ai status <slug>                               # offered, assists used and left
whk ai setup <slug> --request <id> --request <id> --field order --description "the order number"
whk ai setup <slug> --request <id> --layout --description "Acme order confirmations"
whk ai setup <slug> --request <id> --repair '{"name":"order","from":"subject","pattern":"#(\\d+)"}'
```

## layouts

Ready-made [layouts](/docs/layouts) for emails from common senders (Shopify, WooCommerce, Etsy orders and more). `templates` lists them with the fields each reads; `add-template` adds one to the end of an endpoint's layouts (the endpoint's owner only), and emails it matches are parsed from the next one on.

```bash
whk layouts templates <slug>
whk layouts add-template <slug> <template-id>
```

## fields

A dry run of an endpoint's [named email fields](/docs/email-capture#fields-you-pick-out): what they find in a captured email, the endpoint's newest unless `--request` names one. `--fields` tries fields you have not saved, as a JSON list or `@file`; a field with a problem is reported and left out. Nothing is saved.

```bash
whk fields preview <slug>
whk fields preview <slug> --request <id>
whk fields preview <slug> --fields '[{"name":"order","from":"subject","pattern":"#(\\d+)"}]'
```

## destinations

Where an endpoint's captures are [forwarded](/docs/forwarding): up to 10 destinations, each with its own URL, kinds, filter, format, headers, retries and signing secret. Only the endpoint's owner can manage them. `ls` lists them in order with their last 24 hours; `get` shows one.

```bash
whk destinations ls <slug>
whk destinations get <slug> <id>
whk destinations add <slug> --url https://example.com/hooks --header "Authorization: Bearer $HOOK_TOKEN"
whk destinations add <slug> --url https://hooks.slack.com/services/... --http false
whk destinations update <slug> <id> --enabled false
whk destinations reorder <slug> <id> <id>       # first to last
whk destinations rm <slug> <id> --yes
```

`add` and `update` take a flag for each setting, and `update` changes only the ones you pass:

| Flag                                                   | Description                                                                                                                                                              |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `--url`                                                | Where deliveries go (a file drop has none; its server is in `--config`)                                                                                                  |
| `--name`                                               | A name to tell it apart by (`""` clears it)                                                                                                                              |
| `--enabled`, `--http`, `--email`                       | `true` or `false`: on or off, and whether it takes HTTP requests and emails                                                                                              |
| `--format`                                             | `auto`, `as_received`, `json`, `template`, `chat`, `postmark`, `sendgrid`, `mailgun`, `cloudmailin`, `sheets` or `file_drop` ([Formats](/docs/forwarding#formats))       |
| `--filter`                                             | Which captures it gets, as JSON (`{"logic":"and","conditions":[...]}`), `@file`, or `null` for all ([Send only some captures](/docs/forwarding#send-only-some-captures)) |
| `--body-template`                                      | For `template`: the JSON body with `{{ placeholders }}`, or `@file`                                                                                                      |
| `--message-template`                                   | For `chat`: the message text, or `@file` (`""` sends the standard message)                                                                                               |
| `--header "NAME: VALUE"`                               | A header on every delivery, repeatable; the set you pass replaces the stored one, and `NAME` alone keeps that header's stored value. `--clear-headers` removes them all  |
| `--append-path`, `--keep-order`                        | `true` or `false`: append the captured path to the URL, and deliver one at a time in capture order                                                                       |
| `--retry-seconds`                                      | How long failed deliveries are retried: `0` (one try), `3600` or `86400`                                                                                                 |
| `--throttle-seconds`, `--delay-seconds`                | 0 to 3600: at most one delivery every N seconds, and a wait after the capture before the first try                                                                       |
| `--sent-field`                                         | A JSON body field with the sender's own timestamp (`""` clears it)                                                                                                       |
| `--attachments`                                        | How emails' stored attachments travel: `links`, `inline` or `none`                                                                                                       |
| `--config`                                             | For `sheets` and `file_drop`: the spreadsheet and columns, or where files go and what they hold, as JSON or `@file`                                                      |
| `--drop-secret`                                        | Send a file drop's password, private key or S3 secret key again (see below)                                                                                              |
| `--mailgun-signing-key`, `--clear-mailgun-signing-key` | For `mailgun`: send your Mailgun signing key (from `WHK_MAILGUN_SIGNING_KEY`, or typed), or remove it                                                                    |

Secrets are never taken from a flag, where they would stay in your shell history. A [file drop](/docs/forwarding#file-drops)'s password, private key or S3 secret key comes from `WHK_DROP_SECRET`, or is typed at the terminal without being shown: `add` asks for it whenever `--format` is `file_drop`, and `update` sends it with `--drop-secret`, which the server asks for whenever the drop would go to another server, login or bucket, or trust another key. For SFTP a value that holds a private key is sent as the key, anything else as the password. Header values are flags, so give a token as a variable in double quotes (`--header "Authorization: Bearer $HOOK_TOKEN"`): the shell stores the variable's name in its history, not the token. Stored values come back masked. A Google Sheets destination takes the spreadsheet's address as `--url` and its `--config` from `whk google` ([Google Sheets](/docs/forwarding#google-sheets)).

```bash
whk destinations preview <slug> --destination <id>                 # what it would send for the newest request
whk destinations preview <slug> --destination <id> --request <id> --format template --body-template @body.json
whk destinations preview <slug> --url https://example.com/hooks --format json   # one not saved yet
whk destinations test <slug> <id> --yes                            # send one delivery now
whk destinations test <slug> <id> --kind email --yes
whk destinations secret <slug> <id>                                # the whsec_ secret deliveries are signed with
whk destinations secret <slug> <id> --rotate --yes
```

`preview` is a dry run: whether the filter lets the request through (the newest of the kind the destination takes, or a sample, unless `--request` names one) and the exact request it would send, with stored header values masked. The setting flags change a saved destination for the preview only. `test` sends one delivery now, as a real one would go out, and prints the answer; the filter is reported, not applied, and nothing is queued. When the destination does not accept it (`delivered: false`), `test` prints the answer first (the API's JSON with `--json`), then exits with `delivery_failed` (status 1) on stderr. `secret` prints only the secret, so `$(whk destinations secret <slug> <id>)` reads it into a variable; `--rotate` replaces it, and deliveries are signed with the new one at once. `rm`, `test` and `secret --rotate` ask first, and need `--yes` without a terminal. Every subcommand supports `--json`, which prints the API's answer.

## deliveries

The [delivery log](/docs/forwarding#the-delivery-log) of an endpoint's destinations, and sending requests again. Only the endpoint's owner can see the log and redeliver.

```bash
whk deliveries ls <slug>                                  # newest first, 5 by default
whk deliveries ls <slug> --status failed --limit 50       # all, pending, failed or skipped
whk deliveries ls <slug> --destination <id>
whk deliveries ls --request <request-id>                  # one request's deliveries, with each try
whk deliveries summary <slug>                             # last 24 hours, waiting, failed
whk deliveries redeliver <request-id> --yes               # to every destination that takes its kind
whk deliveries redeliver <request-id> --destination <id> --yes   # to one, whatever its filter says
whk deliveries redeliver-failed <slug> --yes              # every request whose latest delivery failed
```

`skipped` deliveries are the ones a filter turned down. Each row ends with its request id and destination id (`requestId` and `destination.id` with `--json`). A full page ends with the command for the next one (`--before` and a row's cursor). `redeliver` takes the request id (the REQUEST column), not the delivery's own id, and `--destination` the DESTINATION column, so a failed row is sent again with `whk deliveries redeliver <request-id> --destination <destination-id>`. It sends the request with each destination's current settings, also when it was never forwarded; `redeliver-failed` sends the failed ones oldest first, at most what fits under each destination's pending cap, and `--destination` limits it to one. Both ask first, and need `--yes` without a terminal.

## sandbox

Webhook capture for AI agents and scripts without an account, and the claim that connects an agent to a human's account ([auth.md](/docs/agents)). Every subcommand runs without prompts and supports `--json`; progress messages go to stderr and are left out with `--json`. Errors carry the server's code (`sandbox_full`, `sandbox_endpoint_limit`, `rate_limited` with its `Retry-After`, `invalid_grant`, ...) and exit with a non-zero status.

```bash
whk sandbox create --json                   # a capture endpoint: slug, url, limits
whk sandbox list                            # endpoints and the remaining budget
whk sandbox get <slug>
whk sandbox delete <slug>                   # frees a slot; the budget is not refunded
whk sandbox requests <slug>                 # newest first, --limit (1-100), --since <ms>
whk sandbox request <request-id>
whk sandbox wait <slug> --timeout 60s       # poll until a request arrives, then print it
whk sandbox status                          # what the credential file holds (never tokens)
whk sandbox connect --email you@example.com # connect the agent to your account
whk sandbox forget --sandbox                # or --claimed, or --all
```

The first `whk sandbox create` registers anonymously, which takes a short proof of work (a second or two of CPU). Later commands, and later processes, reuse that registration until it expires. A sandbox holds up to 3 endpoints at a time, 25 captures per endpoint and 100 in all; everything is deleted after 24 hours. Sandbox endpoints answer every capture with a plain 200: no mock responses, forwarding, signature checks or email.

`whk sandbox wait` counts requests from the last 5 minutes unless `--since` gives a timestamp in milliseconds. `--count <n>` (up to 25, what one endpoint can capture) waits for several and prints them as a list.

### Connecting an agent to an account

```bash
whk sandbox connect --email you@example.com --json
```

```json
{"status":"pending","registration_id":"...","verification_uri":"https://webhooks.cc/agent/claim?attempt=...","user_code":"123456","expires_at":"2026-10-28T12:15:00.000Z","email":"you@example.com"}
{"status":"claimed","registration_id":"...","email":"you@example.com","scope":"webhooks:read webhooks:write","assertion_expires":"2027-01-26T12:00:00.000Z","client_name":"whk-cli","saved_at":"2026-10-28T12:01:10.000Z"}
```

The first line is printed at once: hand the link and the 6-digit code to the human, who signs in (or signs up) with that email address and enters the code. The command keeps polling and prints a second line when the human approves (`claimed`), declines (`declined`), or the code runs out (`expired`, after 15 minutes, or `timeout` when `--timeout` is shorter); anything but `claimed` exits with a non-zero status. When a connection is already saved, it prints `already_connected` and exits without registering again; run `whk sandbox forget --claimed` first to connect another account.

Once connected, the regular commands (`whk list`, `whk create`, `whk requests`, `whk listen`, `whk tunnel`, ...) act for that account whenever no `whk auth login` session exists; a login always wins. The connection lasts 90 days. When the human disconnects the agent under Account, Connected agents, the next command answers `invalid_grant` and the connection is removed from the credential file. The sandbox endpoints of an earlier `whk sandbox create` stay in the sandbox until they expire.

### The credential file

Registrations are saved in a file the CLI shares with the [MCP server](/docs/mcp) and the SDKs, so a connection the human approved once works from every tool and survives restarts:

| Platform | Path                                                                    |
| -------- | ----------------------------------------------------------------------- |
| Linux    | `$XDG_CONFIG_HOME/whk/agent.json`, else `~/.config/whk/agent.json`      |
| macOS    | `~/Library/Application Support/whk/agent.json`                          |
| Windows  | `%APPDATA%\whk\agent.json`                                              |

Set `WHK_AGENT_FILE` to use another path, for example one per CI job. The file is written with mode `0600` and holds identity assertions and short-lived access tokens, so treat it like `token.json`. Entries are kept per API URL (`--api-url`, `WHK_API_URL`), so a local stack never touches production's. `whk sandbox status` shows what is saved without printing any secret.

## api

Call any [API route](/docs/api) with your credentials and print the answer as it arrives. It covers whatever has no command of its own yet.

```bash
whk api /api/endpoints
whk api endpoints/<slug>/alerts
whk api -X PATCH endpoints/<slug> -d '{"retentionDays":7}'
whk api -X PUT endpoints/<slug>/alerts -d @alerts.json
```

The path is relative to `/api` when it does not start with it, and only paths are accepted, so your credentials never go to another host. `-d` sends JSON text, `@file` or `@-` (stdin), with `POST` unless `-X` says otherwise. `-H Key:Value` adds a header and `-i` prints the status and headers to stderr. A failing status prints the body, then exits with the matching status (404 is `not_found`, exit 4). Routes that need a browser session, such as billing and account deletion, refuse API keys.
